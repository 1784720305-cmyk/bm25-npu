# A5 BM25：常驻执行计划、异步传输与分区索引

日期：2026-10-26。状态：源码审计、设计及首版实现完成，本地 Python 检查通过；尚未在 A5 编译或测速，不是性能达标记录。实际入口见 [Graph 常驻执行计划闭环步骤](Graph常驻执行计划闭环步骤.md)。

## 结论与目标

最终架构确定为：**整库原始 TF 索引及分区边界常驻 → CPU 在 Search 内把新查询写入固定锁页缓冲 → 一次重放 H2D、SIMT 评分＋已验收 SIMD 选择、设备合并、D2H → 一次等待 → CPU 返回严格 Top-K。**

首项实现必须是常驻执行计划，复用已经在设备通过的 SIMD 算子。随后接入按词、文章分区预建的边界目录。两部分分别比较，最终组合共同接受完整 Search 验收。停止把“比旧 NPU 快 5%”当作任务完成；成功条件是同边界、同期 NPU 稳定快于合理 CPU。

不能由硬件峰值推导任意小查询都比 CPU 快。本方案针对已经明确的 262144 文档、Q=8、K=10、S=32 主负载；Q=1 的结果必须独立交代。不能把批量耗时除 8 充当单条延迟。

## 1. 基线已经说明什么

前一聊天最后一份用户实机日志中，同期六轮结果如下。数字是六个批次中位数再取中位数，单位 µs，均为八条查询的整批时间。

| 查询组 | CPU32/32 | 已验收 SIMD NPU | NPU/CPU | NPU 获胜轮数 |
|---|---:|---:|---:|---:|
| A | 70.71125 | 140.691 | 1.98966 | 0/6 |
| B | 69.339 | 140.46825 | 2.02582 | 0/6 |

CPU 的较快轮次约 64µs，不能只瞄准较慢轮次。工程目标设为主负载完整 Search **55µs 以内**，为同期竞争留出余量。这是目标预算，绝不是预测或已测数据。最终门槛仍由同期 CPU 实测决定，CPU 更快时随之收紧。

旧 NPU 到 SIMD NPU 的约 24% 改善已证实；旧方案“SIMT 评分＋SIMD 局部选择”已经兑现，不能再次包装成新优化。

## 2. 这次找到的具体问题

`npu_prototype/fused_search_host/fused_search.h::SearchImpl` 的实际热路径是：

1. PackQueries 分配并整理查询。
2. 创建七个临时 aclTensor 描述：offsets、words、debug placeholder、两份分片输出、两份最终输出。
3. 两次同步 aclrtMemcpy 上传 offsets 和 words。
4. 两次 GetWorkspaceSize，重新准备两个 aclOpExecutor；工作区内存复用了，但准备过程仍逐次执行。
5. 分别提交评分选择和合并，等待整个 Stream。
6. 两次同步 aclrtMemcpy 下载 scores 和 ids。
7. 校验结果、销毁临时张量和查询缓冲后停止计时。

**以上是源码事实。它们分别占多少微秒，当前尚无 SIMD 新版的对应实测。** 历史旧链路的 112µs 链外时间和原选择的 72% 周期份额均不能移用到新版。

另一个源码事实：评分每个 query/shard/term 都在 GM 倒排表执行两次 LowerBound；这个边界只由索引和文章分区决定，却被反复查询。主负载每组共 24 个词位置、32 分区，包含已知词时最多执行 1536 次这类查找。CPU 也有类似查找，公平比较时允许它使用相同的预建目录。

没有证据说明四次拷贝的负担来自带宽不足。当前逻辑输入只有 72 字节 offsets＋96 字节词编号，结果 640 字节。应先减少提交、同步和运行时准备，不能用 HBM 峰值解释这些微小传输。

## 4. 热路径重构：固定地址、固定形状、每次更换内容

### 4.1 初始化一次完成

- 保留整库常驻。为一个 session 分配独占输入、输出、工作区、非默认 Stream 和模型运行实例。
- 用 aclrtMallocHost 分配输入及输出锁页 arena；设备侧也分配连续 arena。
- 输入 arena 为 `[int64 offsets[Qcap+1]][padding][int32 terms[Wcap]]`，记录对齐后的词区偏移。tensor 分别指向 arena 内对应地址；不得让两个 tensor 的数据区重叠。
- 输出 arena 为 `[float scores[Qcap*K]][padding][int32 ids[Qcap*K]]`。原合并算子两个输出直接指向它的两段，不新增打包 kernel。
- 在初始化阶段按固定容量创建七个张量及所需工作区。索引张量、描述、arena、工作区在模型销毁前保持有效。
- 在实际 CANN 头文件、动态库和该自定义算子上检查捕获能力。不能仅凭官方页面列出 950 就认定当前安装可用。
- 为固定 Qcap、Wcap、K、S、index_id 构建一个模型实例，捕获：**一次 H2D 整个输入 arena → 已验收评分选择算子 → 已验收合并算子 → 一次 D2H 整个输出 arena**。prepare 在捕获前执行，execute 在捕获中执行。
- 捕获期间不查询或同步 Stream，不调用同步 memcpy。初始化与预热用合成查询，不预计算正式 A/B 的答案。

两个 kernel 仍有真实设备调度成本。捕获只减少 Host 逐次准备和下发，不把两个 kernel 变成单个 kernel，也不保证其设备时间下降。

### 4.2 每次 Search 的完整工作

```text
start = steady_clock::now()
校验原始 grouped IDs、容量和每条最多 64 词
在固定 pinned input 中写入 offsets 与词编号，保留顺序和重复词
写好所有需要覆盖的 padding；真实长度由 offsets 决定
aclmdlRIExecuteAsync(model, stream)
aclrtSynchronizeStream(stream)       // D2H 已在模型内，等待它完成
把 pinned output 复制到返回对象，做原有合法性和排名检查
stop = steady_clock::now()
```

这里缓存的是任务结构，不是查询内容或搜索结果。每次输入写入、H2D、计算、D2H、输出复制及检查全部在计时内。不能把 prepare 挪到每次 Search 的外层调用中伪装成初始化；session 内固定形状的执行计划才允许提前构建。

首次版本固定实际 Q=8 和现有 wordCapacity，A/B、全空及不同词数都用相同 tensor shape；空查询的 offsets 全部合法，words 的固定容量可以非零。已有 kernel 用 offsets 控制有效词区，尾部容量不是查询内容。改变容量要显式建立新的 session，并计入冷启动报告。Q=1/Q=32 分别建相应 session，不让单条查询偷偷等待组批。

当前逻辑输入 168B 不等于 arena 的实际 DMA 字节；对齐、固定容量和 padding 后的 H2D/D2H 字节必须如实记录。同步 Search 返回前不允许再次修改 pinned input 或复用 pinned output。并发需要独立 slot/模型/工作区，首轮先不增加并发。

不能缓存普通 aclOpExecutor 后反复调用，不能对一次性执行器做未经文档支持的重用。复用的是捕获完成的 modelRI。遇到捕获不支持或错误必须明确失败，不悄悄回到旧路径后沿用 Graph 名称报告性能。

销毁先保证在途工作结束，再销毁模型、张量和内存，最后关闭 Stream/context。错误分支也遵守同一资源寿命。

## 5. 设备侧固定改动：索引分区边界提前构建

在建索引阶段为每个词生成 `boundary[term][0..S]`：

```text
boundary[t][s] = lower_bound(posting_doc_ids of t, floor(N*s/S))
begin(t,s) = boundary[t][s]
end(t,s)   = boundary[t][s+1]
```

边界保存为原 posting 数组的全局偏移，首项是 term_offsets[t]，末项是 term_offsets[t+1]。由于当前 postingCount <= INT32_MAX，可以用 int32 非负偏移；首版若为降低 ABI 风险沿用 int64，空间为 `8*V*(S+1)`，S32 即每词 264B。两者必须在实现前选定，不能主机与设备使用不同宽度。正式首版选 **int64**。

目录基于整库和分区生成，与请求、词频统计结果和 Top-K 答案无关，随 index_id、N、S 一起校验并上传一次。可以沿已排序倒排表顺序构建；空区间保留相同 begin/end。不预计算 contribution，不修改 TF、IDF、docNorm 或 FP32 运算次序。

评分原来的两个 LowerBound 替换为相邻目录读取；未知词仍跳过，重复词仍按原顺序重算重加。SIMT 评分、SIMD 选择、严格同分收集与已有合并保持现有算法。该改动有额外 GM 读取和目录空间，收益必须实测；不能把消除 1536 次查找直接换算成某个加速倍数。

公平基线保留原 CPU32/32，同时让 CPU 使用同一目录作为额外对手；最终比较取两者较快者，并补此前合理线程配置的候选。不能让新 NPU 独享无查询依赖的预处理后把全部收益归为硬件。CPU 获得此优化后仍快时，任务仍未完成。

本轮不新增官方 TopK 运行时依赖，不重复移植已经落地的 histogram 选择，不改变精度、不删除 term 间的必要同步，也不在一个普通 kernel 内使用未经证明安全的跨 AIV 自旋屏障来融合最终合并。

## 6. 预算、实验与明确的完成条件

55µs 的设计预算可以分配为：Host 整理和结果处理 5µs、计算跨度以外的传输与调度开销 15µs、评分选择 30µs、合并 5µs。**这些只是同一关键路径的工程预算，不是测得的阶段中位数，不能用于宣称可实现。** Stream 等待函数包含计算，不能把它的全部耗时再加到 kernel 时间上。若实际 kernel 链本身超过预算，Graph 也不能单独解决。

执行顺序固定：

1. 记录已验收 SIMD vendor、调用器、索引、CPU 和实际运行库指纹；保存最新六轮基线摘要。
2. 实现固定 arena＋异步链，先用原两个算子核对；再捕获同一条链并核对。保留“原路径、异步路径、Graph 路径”的完整 Search 对照，区分拷贝与捕获各自收益。
3. 在 Graph 路径上接入分区边界目录，做新旧评分全分数和最终排名检查；CPU 同目录版本也核对和测速。
4. 单次短诊断确认实际 replay 的 H2D、两个 kernel、D2H 都存在；按同次调用核对 Host 总时间和计算链跨度。分布统计先对每次样本计算，再汇总；不相减不同轮次或不同版本的中位数。采集下时间不替代普通基准。
5. 使用未采集的完整 Search 做六轮交替进程顺序，既有预热 5 次、正式 30 次，A/B 都测。保存全部样本、中位数及 p95，与原 CPU32/32 和同目录 CPU 同期比较；不能只在赢过旧 NPU 后才显示 CPU 差距。

受影响正确性包括：A/B/A/空/B、相同形状不同词数和未知词、重复词、词数 0/64、容量拒绝、输出保护区、固定 arena 的尾部残留、索引不变；分区边界词表空列表和文档分界；严格零分补齐、相邻 FP32 分数及真实 ID 同分规则。旧 selector 内部算法不变，不重跑与改动无关的全套设备算子测试。

**主负载完成条件：** A/B 每轮 NPU 中位数都小于当轮合理 CPU 对手中最快的中位数，六轮全胜；两组 p95 汇总也优于对手；正确性、真实新输入重放和计时边界全部通过。55µs 为留余量目标，不替代这条相对验收。六轮是工程验收，不声称普适统计证明。

Q=1、Q=32、较密命中各补一组范围验证，单独报告延迟与吞吐。主负载通过只能声称该范围胜出；如果还要求 Q1 也胜出，就把它加入完成门槛，不能用 Q8 代替。BM25S 原版 Numba 同边界对照保留，但不能取代更快的优化 C++ 对手。

如果 Graph＋分区目录仍未赢，保存失败结果，继续以该实际链路的关键路径解决剩余差距；此时本方案不构成“性能已完成”的交付，也不能回到只报告新旧 NPU 百分比的循环。

| 新增或改动位置 | 职责 |

| 新的独立 `npu_prototype/graph_search_host/` | 固定 arena、锁页内存、固定描述、捕获/重放、资源寿命、完整 Search 计时 |

| 独立分区目录构建及校验工具 | 全词边界、index_id/N/S/偏移类型和字节数；不修改原索引文件 |

上述实现已落地，其中分区目录在 CPU/NPU session 初始化时由同一 portable 构建器产生；函数 ABI 不变，首个输入张量形状按目录合同验证。当前本机是 Windows，未发现 CANN 或 npu-smi；用户确认由其在黄区执行。尚无本次 Graph/目录候选的设备执行证据。
