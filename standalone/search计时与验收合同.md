# BM25 A5 最终search计时与验收合同

本合同按用户和MT的最终要求固定，优先于历史计算实验的计时说明。目标是“整库索引提前放在NPU，每次收到不同查询后，由NPU查索引并计算”。当前新索引只完成主机格式；新NPU查询评分及常驻会话尚未实现，不因本合同建立而视为完成。

## 唯一的正式search主指标

**CPU已有查询词编号 → 开始计时 → 上传查询 → NPU检索 → CPU收到Top-K → 停止计时。**

NPU路径的检索包括按词编号查整库索引、算贡献、累加文章分数、Top-K选择及合并。使用主机单调时钟测整段墙钟时间；设备只提交但还未完成，或Top-K仍在设备上，都不能停止计时。同步和必要结果下载必须完成。

CPU路径：**CPU已有相同查询词编号 → 开始计时 → 从内存索引检索 → CPU得到Top-K → 停止计时。** CPU没有上传步骤，不虚构一项传输费用；从相同逻辑输入到相同逻辑输出采用同一边界。允许合理优化、多线程以及提前建立并常驻内存的索引。

“已有词编号”不等于“已经查好索引并展开了文章记录”。默认公共调用输入为按查询分组的原始词编号。若实现需要把它们转成连续INT32数组、构造INT64查询边界、转换后端类型、过滤未知词或为外部库生成兼容输入，这些请求相关的处理均在计时内。不能让NPU先取得查好的TF/IDF/长度项/分组表后才开始计时。

最终输出是CPU可用的K个文章编号及FP32分数。为满足“分数降序、同分文章编号升序”的必要结果转换/修正也在计时内；不能在停表后补排名。独立公式核对、调试保存文件和对照答案检查在计时外，不作为生产search工作；正常API必要的请求检查仍在计时内。

## 哪些可提前完成，哪些必须计入

| 工作 | 正式search如何处理 |
|---|---|
| 文本分词、文本到词编号 | CPU/NPU统一放在边界之前，单独报告；有需要再另报文本到结果总时间 |
| 语料TF/DF、文章长度、IDF、建索引、静态索引格式转换 | 可提前完成，单列建索引时间和体积；不能依赖本次查询预先查出命中文章 |
| 索引文件读取、静态完整性校验、ACL初始化、整库上传 | 常驻服务初始化单列；一次会话完成后，后续不同查询复用该索引 |
| 预分配服务容量内的通用输入/输出/临时缓冲 | 可在初始化完成，明确容量与内存；不是提前生成某条查询的内容 |
| 每次请求的词编号整理、边界生成、必要类型/库兼容转换 | 在search计时内，CPU/NPU各自所需工作都计入 |
| 查询输入上传、请求相关接口准备、提交和同步 | 在NPU search计时内，不把同步移到停表之后 |
| 查询时取数、贡献计算、累加、清零、Top-K及合并 | 在search计时内，包括为了避免上一请求残留而必须进行的处理 |
| 最终Top-K下载及满足公共输出规则的必要处理 | 在search计时内；必须CPU已经可用才能停表 |
| 容量不足引起的扩容/额外分配或索引重新加载 | 若真实请求会触发，计入该请求并标记；或明确拒绝超出已声明容量的请求，不能暗中排除 |
| 调试中间结果下载、逐项参考核对、日志/磁盘输出 | 单列，正式计时外；必须区分生产确实不需要的调试与生产必需处理 |

初始化、首次调用及可能的CPU JIT编译单列；稳态可以预热，但不能预存查询结果，不能把未来请求的索引查找、数组展开或传输当作预热。冷启动也需报告，不与稳态混为一项。

## 旧结果重新定性：不能改名成为search

| 已有实验 | 实际边界与结论 |
|---|---|
| NPU约0.37ms的resident | 已展开的同一批TF/IDF/长度项/分组表提前上传，计时主要是接口准备、提交及同步；只作为计算实验 |
| NPU约2.24092ms的with_transfers | 从已展开主机数组开始，包含这些数组上传、四段计算/同步和最终Top-K下载；不含CPU生成展开输入，因此仍不是本合同的完整search |
| 自研C++CPU旧计时 | 从已展开TF/IDF/长度项/分组表开始计算，不含原始查询词编号的取数/整理；是同流程计算对手，不能改称常驻索引CPU search |
| 已有原版BM25S NumPy参考 | 提前建好贡献索引是允许的；当前包装器还在计时前做未知词过滤/空查询兼容变换，最终search对照需移入计时；原生同分差异单列，严格规则适配另报且必要修正在计时内 |
| 新resident_index.py准备/诊断 | 仅构建文件、检查格式与公式，没有新NPU查询执行或search计时 |

这些旧数据和原始日志保留其原有边界，不改历史样本。最终search加速比只能由符合本合同的新CPU/NPU实验产生。

源码核对依据：

- `npu_prototype/sharded_host/sharded_benchmark.cpp`中`iteration`的起点在`upload`前；`with_transfers`调用`downloadTop`后取终点；`resident`在首次调用前上传一次。读输入文件和CPU输入展开均不在该计时段。
- `cpu_reference/cpu_runner.cpp`在测量前读取四组已展开数组，正式循环只计`compute()`的贡献、累加和Top-K。
- `standalone/run_bm25s_reference.py`在`measure`之前构造`queries`，过滤越界词并将空查询映射到兼容列；因此当前CPU参考也需要新的公共search入口，而不是只修NPU一侧的名字。

这里是源码事实；将新数据组织接到950后的实际耗时仍未知。

## 下一阶段代码必须满足的条件

1. 常驻的是整库静态倒排索引，包含未被预热/测试查询用过的词；不能只缓存某一批查询展开数据。
2. 一个服务进程初始化一次整库，连续处理不同查询。每次只上传查询词编号/查询边界及必要请求控制信息，不再上传逐命中文章的TF、IDF、长度项或Q×N分组表。查询整理本身仍计时。
3. 新NPU评分算子从索引取数并算总分，随后复用已验收的局部Top-K和合并。不能在CPU查好整批记录，再宣称查询只传词编号。
4. CPU新对照同样以常驻索引＋原始词编号为输入，保留合理优化；现有C++展开计算路径继续作算子级辅助对照。
5. 公式、FP32精度、未知/空查询、重复词、同分规则及原容差不改。BM25S保留原版及其原生结果说明，严格适配单独命名。BM25S预计算贡献与NPU查询时算公式是算法差异，不能全部归因于硬件。
6. 在同进程先做A/B/A及更多混合查询正确性：不同命中文章、空/未知/重复词、不同长度和K，检查全部文章总分及最终编号；检查索引不变、没有旧输出残留、没有CPU结果替代设备输出。
7. 记录整库上传次数/字节、每次查询上传/下载字节和实际索引身份，证明新增查询没有触发整库重传或主机展开。文件格式28/168字节只是数组大小，不能代替这些运行记录。
8. 性能测量复用已就绪索引，正式计时处理多条新查询，保留全部样本、中位数/p95及设备/线程/批量/版本/容量信息；预热、核对和采集与正式计时区分。单条Q=1延迟与批量吞吐分别报告，不把批次时间除以Q叫作单条查询延迟。

正式报告至少分开列：冷启动/索引准备，Q=1 search延迟，固定批量search耗时与吞吐，计算诊断。只有查询相关处理＋传输＋CPU获得结果的search指标用于本任务最终达标判定；计算诊断可定位瓶颈，不能替代最终指标。

## 本次结论

最终要求已固定；现有主机索引格式与此方向一致，但文件准备不等于NPU常驻服务实现。下一步继续索引文件验收、新评分算子、常驻调用器及同边界CPU入口，再做设备正确性和正式search比较。ATC/.om、Faiss或IndexSDK不是新主线的运行依赖。
