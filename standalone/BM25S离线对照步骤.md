# 原版BM25S离线CPU对照

**黄区NumPy阶段已完成：** 64K/Q1和256K/Q8分数及严格适配通过；256K/Q8原版5条同分编号差异保留。本页首次执行命令为复现记录。下一步见 [原版Numba离线步骤](BM25SNumba离线步骤.md)，不重跑已有目录或修改原库。

## 为什么现在做

候选收集版已在用户950上编译、安装，25组独立设备验收、四段小样本、大样本和CPU结果核对通过。同卡六轮对原Radix：64K/Q1/K10基本持平，256K/Q1/K10耗时减少约6.6%，256K/Q8/K10约9.8%，256K/Q8/K32约3.4%。均为准备好输入、驻留设备的四段计时，当前只保留已测场景的结论，不设自动切换阈值。

对当前8线程/8文章分区CPU，256K/Q8/K10新版赢6/6轮，配对比值中位数约1.128；256K/Q1/K10仅赢1/6轮。合理CPU更广配置与整机最优尚未确定。

用户新测256K/Q8/K10含传输：正确性通过，30个测量样本整批中位数2.24092ms；接口准备中位数0.004737ms、四次提交和同步中位数0.408012ms。不同阶段中位数不能直接相减当精确传输耗时，也不拿历史CPU样本计算正式加速比。日志与当前代码显示，每轮上传TF、长度项、IDF和INT64分组位置，返回最终Top-K；输入尺寸推得上传19091892字节，其中分组位置16777224字节，返回640字节。当前逐批展开/上传路线尚未证明完整查询优势。

现在暂停新增Top-K内核，先跑成熟CPU参考。BM25S建索引时存好词对文章的贡献，查询时累加并选K；NPU第一版在查询时算贡献，两者计算流程不同。比较结果必须注明这个差别，不能全部归因于硬件。

## 输入、处理、输出和验收

输入直接使用已有`scale_fixture.py`目录中的`corpus.json`及对应元信息/输入/期望文件。文章是已分词的整数词编号，不重新分词、不重新生成另一份随机语料。脚本确认语料及四份数组的指纹，用原始文章独立重算DF、平均长度和高精度公式，再核对现有参考及原BM25S的全部文章分数。仍使用`1e-6 + 2e-6*abs(expected)`，不放宽。

处理步骤：

1. 读取随包提供的原版25文件及固定提交，验证逐文件SHA256，再加载这份原库。无需联网或pip安装。
2. 原版公开API建索引，参数`method=atire`、`idf_method=lucene`、k1=1.2、b=0.75、FP32、NumPy查询/选择及NumPy CSC构建。建索引和预计算单独记录，不计查询时间。
3. 对全部查询核对完整分数；重复词重复计入、未知词忽略、空查询用原索引中明确建立的零列编码。严格排名用独立完整排序核对，不用分数容差把近似相等强行认成同分。
4. 分别计时原版`retrieve`和外部严格规则适配。每次查询计时之外检查全部返回结果，保存每个计时样本、中位数/p95、索引数组大小、原版源码/输入指纹、原版实际完整分数及实际返回结果。

原版NumPy选择先`argpartition`，再排序K项，没有严格保证同分编号升序。原版结果只要成员分数确为前K大、无重复/越界且FP32字节来自自己的分数数组，其原生语义检查可以通过；若不同于我们的规则，`native_matches_strict_id_contract=false`并列出差异行，不能把它写成严格规则通过。

外部适配调用原版`get_scores_from_ids`，用精确第K分数门槛收齐严格高分，再按编号补门槛同分，最后排序选中的K项。原库不改，正负零同分，输出原FP32字节。它与独立完整排序、原始语料公式严格编号相同才通过。两个路径分别计时，不把适配路径记成原版`retrieve`成绩；因为选择算法不同，也不能简单相减得到“同分修正本身的耗时”。

输出目录含`report.json`、`bm25s_full_scores.bin`以及各配置实际Top-K分数/INT64编号文件。失败/中断保留部分报告，不记为成功，不从参考文件复制答案当作BM25S输出，不覆盖已有结果目录。

关键函数对应关系：

| 函数 | 可以向MT这样解释 |
|---|---|
| `check_source` / `load_reference` | 先查固定版本和文件字节，再加载随包的原库，防止误用环境里的另一版 |
| `independent_formula` | 从原文章单独核对公式；这份答案只用于验收，不进入计时或替代原库输出 |
| `native_call` | 直接调用未改的BM25S公开`retrieve`，明确NumPy后端 |
| `strict_select` / `adapted_call` | 外部严格规则版本：取原库总分，按门槛和文章编号选K；原版API的计时单独保留 |
| `check_selection` / `measure` | 每次只计实际调用耗时，返回后再查所有结果；原版同分差异与严格规则验收分别记录 |

## 黄区条件及限制

用户已确认Python3.9.9、NumPy2.0.2、SciPy1.13.1，尚无Numba/BM25S。第一版固定NumPy后端，原版源码随本包提供，Numba等可选依赖不需要安装。若存在JAX，本参考进程明确设`JAX_PLATFORMS=cpu`，原版可选导入探测也不使用设备；正式选择明确`numpy`，不走`auto`。

这只是当前可运行的NumPy参考，不冒充最佳BM25S。后续根据测量与目标环境，再准备可核对的离线Numba依赖；不能因为Numba缺失就宣布NPU战胜成熟CPU最优实现。

BM25S线程参数并行的是多条查询，和C++CPU把同一条查询的文章分成8份不同。Q=1时即使线程上限设8，最多仍只有1条查询工作，不称为8核单查询计算。报告保存1和8的配置，选更快配置时要保留其余结果。

本机Python3.10/NumPy2.2.6实际运行原版及249项独立公式、同分、原分数字节、来源、输出指纹与失败保护检查通过；另在4096文章/8查询通过。测试也在新进程阻断Numba/SciPy/JAX等可选导入，验证NumPy路线可运行。不是黄区Python3.9/NumPy2.0.2实测，不把本机CPU计时作为950成绩。
