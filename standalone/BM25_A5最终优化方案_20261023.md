# BM25 A5 最终优化方案：SIMT评分与950向量选择在片上协作

日期：2026-10-23。本轮是源码复核与方案冻结，没有新增、编译或运行优化内核。原256线程融合版继续作为正式基线。这里的“最终”指收敛实施范围和验收规则，不代表尚未实现的方案已保证超过CPU。

## 先用简单的话说明

我们已经把索引长期放在NPU，并把评分和局部选K放进同一个算子。现在的问题是：评分之后，仍让大量SIMT线程反复向计数桶加一、扫描大表、等待同步。最新诊断说明选K值得优先处理，但没有证明其中的原子操作就是唯一瓶颈。

组内IndexSDK给出的更直接做法是：**SIMT负责适合并行查找的计算，结果留在片上内存；再由昇腾的向量指令做批量选择，最后只把少量候选交出去合并。** 自研不需要把所有步骤都强行写成SIMT，也不需要继续发明Top-K算法。

最终主线确定为：

**常驻原始TF索引 → 查询词编号上传 → 自研SIMT评分及已有正分压缩 → 自研950 SIMD向量阈值选择 → 严格同分处理/只排序最终K个 → 已有NPU合并 → CPU收到Top-K。**

只落地这一套候选，替换局部选择的执行方式。保留当前256线程评分、FP32公式与查询词累加顺序、索引格式、分片数、合并算子、CPU实现和公开Search计时边界。上次提出的“同桶原子请求合并”不再作为下一项主线；72%的阶段占比不足以单独支持它。

## 3. 唯一实施候选：片上混合选择

### 输入、处理、输出

输入不变：整库原始TF倒排、docNorm、IDF提前常驻NPU；每次只上传原始分组查询词编号。首个性能验收固定262144篇、8条查询、K=10、S=32；随后才补K<=32与其他批量的范围。

一个AIV工作块按原任务编号处理自己的文章分片：

1. **SIMT评分。** 复用已验收的索引范围查找与FP32贡献计算，按原查询词顺序累加，分数仍留在UB。重复词不能去重或改变加法顺序。
2. **沿用正分压缩。** 正分不超过1024时，得到“原始分数位+真实文章编号”的紧凑列表。当前A/B实测每块约730个正分，历史最大800/825，是该快路的现实依据。不是把1024定成可以截断的上限。
3. **SIMD向量选择。** 自己编写32位比较键与掩码，参考官方B32向量统计模式，每轮8位、256桶，从高位到低位最多4轮确定第K大边界。用硬件`Histograms`处理一批键，替代每条记录一次线程UB原子操作及2048桶的线程协作扫描。256桶边界选择也使用向量前缀/归约方式设计；不退化为AICore标量逐桶长循环。实际所需API先核对安装头文件。
4. **精确收集。** 保留全部严格优于边界的文章；不足K个的等分成员按真实文章编号升序补足。最多只给最终32槽排序。沿用已验证的ScoreKey零值归一规则，输出分数始终从原FP32位复制。
5. **复用最终合并。** 每分片仍输出K个，调用现有自研NPU合并。分片内提前截断只发生在文章完整总分算完之后。

正分少于或等于K、全零等情况保留现有精确路径；正分超过1024时使用已验收的设备选择路径，不截断、不用CPU代算、不把该分支伪称新快路。稠密负载的适用范围单列。

评分和SIMD选择在**同一个Ascend C算子调用内**完成，不新增ACLNN提交，不把完整分数写入GM再读回。可以像IndexSDK一样在AIV侧任务循环里依次调用评分VF、向量选择和最终收集VF；这会增加核内VF切换和依赖同步，必须计入性能与资源检查，不能声称“融合所以没有成本”。

### 省掉什么，又增加什么

| 部分 | 拟省掉的工作 | 新增/保留成本及限制 |
|---|---|---|
| 分桶统计 | 大量线程同址原子加、SIMT大桶清零与分桶前缀协作 | SIMD键转换、向量统计及掩码操作；8位分桶最多4轮，比原三轮多一轮 |
| 前缀与边界 | 256线程对2048桶进行扫描与多次块同步 | 256桶的向量扫描/边界提取，以及必要的SIMT/SIMD依赖同步 |
| 候选处理 | 不排序每批32个输入，不为每线程保存K长名单 | 保留正分压缩与真实ID携带；边界同分仍需精确选最小ID |
| 寄存器 | 尝试让评分和选择不再挤在同一SIMT VF的活跃变量集合里 | 是否降低寄存器/栈必须看编译报告，不承诺下降幅度或实际占用率 |
| 内存 | 不新增八份直方图，不增加中间GM分数 | 为256桶/向量临时量重新审计复用区；目标仍为64KiB动态UB，不能挤占缓存后再宣称“空间足够” |

显式缓冲初步预算：完整局部分数32768字节、评分元数据1344字节、1024正分的位/ID共8192字节、最终候选256字节，合计42560字节；原50848字节上限还余8288字节，供向量统计、掩码与对齐使用。这只是布局预算，不是已编译资源证明；若实际API必须使用更多临时空间，先给出完整布局与缓存影响，不静默提高UB声明。

整数计数可用的位宽由每块最多8192条决定；这不意味着将FP32分数降精度。取32位键的8位片段只是精确选择步骤，不是量化或近似Top-K。

## 4. 为什么最终优先选它

**源码事实：** IndexSDK已经展示同一AIV内SIMT计算接向量TopK；官方950 B32源码已经使用向量寄存器硬件Histograms；DeepSelect昇腾实现也主要使用SIMD筛选与压缩。它们共同指向950具体执行单元的分工。

**设计推断：** 当前输入已经在UB，约730条正分却仍通过2048桶SIMT循环选择，值得把统计/扫描整体迁到向量执行方式。这比在未证实的单个原子热点上继续增加专用缓冲更有完整的硬件依据。

**必须实测：** 4轮向量选择和核内切换能否胜过原三轮；快路是否确实触发；寄存器、栈、向量临时量和缓存影响；严格同分处理是否抵消收益。GPU的算法阈值与加速倍数不作为950证据。

暂缓三项：完整CUDA WarpSelect移植、BM25贡献预计算、进一步改变稀疏索引/只处理命中文章。它们分别涉及另一套Warp同步/寄存器队列、CPU/NPU工作量变化和评分数据组织变化；本次不把这些不同路线叠加成无法归因的大改动。

## 5. 一次上机闭环与停止规则

### 上机前本地集中准备

- 冻结当前正式256线程版、合并、CPU与Search边界，使用独立工程/vendor，不覆盖既有验收。
- 源码实现只覆盖上述一个候选；准备独立CPU规则模型及受影响边界，不扩写搜索系统。
- 准备一条失败即停的编排：读取并核对实际MicroAPI声明 → 编译并保存各VF/SIMD资源报告 → 安装 → 读取实际生成aclnn头文件 → 核对ABI及二进制归属 → 必要设备正确性 → 完整Search新旧对照 → 达到保留门槛才同期测CPU。
- 实际接口未知时，先完成不依赖该声明的源码、调用与验收准备；接口读取与编译门禁在黄区脚本内处理，尽量避免每核对一项就重新提交。

### 只重跑受影响的正确性

当前负载A/B交替复用；核对调试全分数、局部分片K、最终K、原FP32位、保护区及索引不变。正分数量0、K-1、K、K+1、1023、1024、1025；K=1/10/32；全同分、跨分片同分、正负零、很小正数、紧邻FP32、尾部非整向量、原ID打乱后的比较；只用小数据补规则边界。

不重复已经通过且不受改动影响的整套TF/DF、CPU Top-K、旧算子和旧计时诊断。新选择若失败，记录首个差异并停止，不运行性能阶段。

### 正式性能只认完整Search

固定CPU已有查询词编号后开始计时，包含查询整理/上传、设备查索引/计算/选择/合并、同步、Top-K下载与边界内必要清理，到CPU收到结果结束。新旧共用原Search入口，不移走查询工作。

1. 原256线程版与候选，六轮独立进程交替顺序，每轮预热5次、记录30次；保留全部样本、各轮中位数和p95。
2. A/B均快6/6轮、中位数汇总至少改善5%、p95汇总不退化，才保留候选。这是已有工程门槛，不是普遍统计证明或最终CPU达标门槛。
3. 达到保留门槛后，立即与同一时段、相近负载的原CPU32/32作六轮交替完整Search对照；不能挑慢CPU轮次。CPU仍更快就报告尚未达标。
4. 主负载闭环后，只补同库Q=1、Q=32及一组更密命中负载，报告快路比例与单条/整批区别。Q8批次时间除8不能叫单条延迟，不用一个合成样本宣称通用胜出。
5. 用已有原版BM25S NumPy/Numba入口完成同边界检索对照，预热/JIT不混入稳态；原生同分与严格适配分开。BM25S预计算、我方查询时算公式的差别写清，不把差值全部归因硬件。

如果混合候选没有稳定改善，明确保留原256线程版，结束这一轮候选实现；不追加桶数、线程数、队列和私有直方图的连续扫描。如果改善但仍未超过CPU，交付真实差距与适用范围，不把“小于旧NPU”写成任务完成。进一步更换索引或预计算属于另一个需单独比较CPU/NPU规则的方案，不能悄悄混入本次结论。
