# 新查询评分算子：整库索引＋词编号 → 文章分数

## 这次实现什么

已有倒排索引存“每个词在哪些文章出现、出现几次”。新增自研`Bm25QueryScore`读取整库索引和一批查询词编号，在NPU上完成取数、BM25贡献计算和文章累加，输出`[查询数, 文章数]`的FP32分数。

它替换的是旧四段链中“CPU先展开输入，再分别调用贡献和累加”的部分。局部Top-K和合并继续保留，不新增Top-K算法，不依赖Faiss、IndexSDK或BM25S运行库，也不使用ATC/.om。

**当前状态：评分算子、独立ACLNN主机程序已编译安装/构建，实际接口和符号来源核对通过。用户已在设备4完成小样本A/B/A/全空/B五批评分：独立公式、重复字节和索引一次上传/回读不变均通过。** 下一步按[常驻评分边界验收](常驻评分边界验收步骤.md)补跨2048篇文章分块及更多查询；Top-K和search性能尚未验收。本地模型/协议检查不能替代设备边界证据。

最终性能边界仍以[search计时与验收合同](search计时与验收合同.md)为准。本次已经证明小样本会话内整库驻留及连续换查询，但还没有完成包含Top-K的完整search。原约0.37ms计算实验和约2.24ms旧传输实验不改名为最终search成绩。

## 输入、处理和输出

7个输入按以下顺序定义，均为一维ND数组：

| 序号/输入 | 类型 | 含义 |
|---|---|---|
| 0 `term_offsets` | INT64 | 每个词的倒排记录边界，V+1项 |
| 1 `posting_doc_ids` | INT32 | 全库倒排文章编号，M项；同词内严格递增且不重复 |
| 2 `posting_tf` | FP32 | 对应TF，M项 |
| 3 `doc_norm` | FP32 | 全库文章长度项，N项 |
| 4 `idf` | FP32 | 全词表IDF，V项 |
| 5 `query_offsets` | INT64 | 每条查询的词编号边界，Q+1项 |
| 6 `query_term_ids` | INT32 | 本批查询的连续词编号；保留重复、顺序和未知词 |

前5组是静态索引，已由评分会话调用器上传一次；后2组随请求上传。小样本五批实际设备复用已通过。

输出` scores[Q,N] `包含每篇文章的分数，包括完全没命中的零分文章，供已有Top-K使用。所有文章位置都必须覆盖写入，不能保留上一条查询的值。

空查询的逻辑词编号数组可以为空。为避免依赖CANN对零维长度Tensor的特殊支持，本算子要求词编号Tensor物理长度至少1：全空批次提供一个未使用的INT32元素，查询边界仍全为0，内核不会读取这个元素。不能把它计成真实查询词；后续调用器分别记录逻辑/物理上传字节。

主机须在初始化核对静态索引的指纹、TF、边界、排序与唯一性，并在每次search内检查/整理查询；物理Tensor容量与查询边界也要一致。形状检查不能代替这些内容检查。第一版N/M/Q×N<=INT32_MAX，其他限制沿用[整库格式](整库常驻索引路线.md)。

## 内核如何做

`QueryScoreSimt`每块128个SIMT线程，处理一条查询的一段最多2048篇文章。块数读取设备可用AIV核数，并采用任务轮转，不能写死卡上核心数。

1. 在明确申请的UB临时缓冲中，将本段文章分数清零；读取本条查询边界。
2. 按查询词原顺序逐个处理。未知非负词直接跳过，重复词重新计分，空查询仍写出零分。
3. `LowerBound`在该词有序倒排表里找出属于本段文章的记录起止；不把范围外记录展开到主机。
4. 线程分摊这些记录，计算`(idf × (tf × 2.2F)) / (tf + doc_norm)`，再累加到UB中该文章的位置。同词倒排表每篇文章只出现一次，所以每一词阶段每篇文章只有一个写入线程；不同文章段也只有一个块负责。
5. 词之间同步，保证上一个词累加完成后再处理下一个词。共享错误标记的读取也有同步保护，不能让某些线程退出而其他线程等待。
6. 将本段完整分数写回NPU全局内存，包括零分；同步后才允许复用UB处理下一个任务。

算法本身无浮点原子累加；仅遇到坏输入时对整数错误标记做原子计数。能检测到的非法边界/负查询编号/被读取的非法数值，使受影响文章段输出-1，后续主机必须当失败停止。其余索引合法性由初始化内容检查负责，不能依靠内核重复检查整库。

UB算法缓冲8256字节，包括2048个FP32分数及边界/控制区；Host还保留32KiB SIMT局部内存预算并核对设备UB容量。GM临时内存只请求框架系统工作区，不重新生成逐查询TF/IDF/长度项/分组表。索引、完整Q×N分数及Top-K中间数组仍占设备内存，尚未优化掉。

每个查询词的二分定位、UB分数清零、同步和完整分数写出均有成本。这版选择的依据是明确的数据复用及无竞争累加，不保证优于其他策略；是否保留和如何调分块必须根据950的正确性与采集结果决定。

## 关键源码

- `npu_prototype/query_score/op_host/bm25_query_score.cpp`：`DecodeShapes`核对7个输入尺寸，`InferShape`推导Q×N输出，`Tiling`按实际核心数划分任务并检查输出、UB/工作区预算。
- `npu_prototype/query_score/op_kernel/bm25_query_score.cpp`：`LowerBound`查文章范围，`QueryScoreSimt`取倒排、算贡献、按词序累加并覆盖输出。
- `standalone/query_score_fixture.py`：准备同一整库下的A/B/全空查询，以及仅用于核对的独立原始语料公式分数。`check`只核对文件，不能证明文件确由NPU产生。
- `standalone/test_query_score.py`：Python分块模型与另一套按词累加诊断逐位比较，随机线程/块处理顺序检查唯一写入、2048分界与尾段、同缓冲A/B/A/空查询覆盖、113项检查；还实际执行`create_project.populate`检查源码字节、备份及预设格式，不调用msopgen或CANN编译器。
- `standalone/create_project.py --operator query_score`：使用黄区msopgen生成新工程，再放入自研源码；固定独立vendor`bm25_query_score`，不覆盖旧算子。

每一步成功再继续，输出目录存在就换新名字，不删除原工程/结果。

先拉取本次更新，核对包、模型与小样本（不运行NPU）：

```bash
cd /test/w50066029/bm25-npu
git pull --ff-only
python3 verify_package.py
python3 standalone/test_query_score.py
python3 standalone/query_score_fixture.py prepare --output results/query_score_small_input1
```

加载CANN并生成独立新工程。沿用已在本机环境确认的msopgen目标和显式Python启动方式：

```bash
source /usr/local/Ascend/cann-9.2.0/set_env.sh
python3 standalone/create_project.py --operator query_score --compute-resource ai_core-ascend950 --compute-unit ascend950 --msopgen-python python3
```

生成成功后编译，保存日志：

```bash
cd /test/w50066029/bm25-npu/results/Bm25QueryScore
set -o pipefail
bash build.sh 2>&1 | tee ../query_score_build1.log
```

如果失败，在黄区查看日志末尾；只分享允许的终端错误摘要，不导出黄区文件。不要继续安装或运行，更不能把模型通过写成算子编译通过。

只有构建成功并确认生成了安装包后，才执行安装：

```bash
bash build_out/custom_opp_openEuler_x86_64.run --install-path=/test/w50066029/bm25-npu/results/custom_opp
```

安装成功后核对实际头文件及依赖（头文件仅查看，不修改）：

```bash

ldd -r /test/w50066029/bm25-npu/results/custom_opp/vendors/bm25_query_score/op_api/lib/libcust_opapi.so
```
