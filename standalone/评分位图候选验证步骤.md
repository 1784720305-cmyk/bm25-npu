# 评分时生成正分位图：独立候选验证

## 判断与修正

方向可以验证，尚不能判断会更快。现有融合算子评分结束后，`PackForSimd`再完整读取每叶最多8192个分数，验证并生成正分成员位图。候选在评分时、文章分数首次由0变正时置位，压缩前改为读取位图并做整数popcount，省掉这次全叶读取/比较。评分公式、FP32加法顺序、查询词顺序、原寄存器阈值、压缩顺序、真实编号同分排名和容量外回退不变。

另一模型的原草稿有三处需要修正：

1. 位图写到`thread`，但评分线程按倒排位置分工，压缩线程按`local % kThreads`分工，两者通常不同。例如同一词的倒排为文章0、256、512，分别由线程0、1、2处理，三个文章的位图却都归线程0，位分别为0、1、2。现按文章编号计算owner。
2. 改成正确owner后，多个线程可能同时改同一个32位字，普通`|=`会丢位。现使用SIMT `asc_atomic_or`；UB复用原owner scratch，仍无新增UB。评分开始时清零两个owner数组，评分词间保留原屏障，压缩先将位图读入寄存器后复用原scratch。
3. 原脚本复制了旧26万篇闭环，既不能评价已达标的千万篇路线，也没有与已测新NPU同期对比。现接入`large_scale_close1`的原始索引、独立FP32参考、全局编号叶块、分级合并和已编译主机；不重新生成千万篇语料，不重建CPU、主机或合并算子。

前一版替换模板不匹配和正分不足K时模型缺少零分补位，也已修正。模型现显式模拟倒排位置所属线程，并有能拒绝旧owner错误的回归；不能用假定文档归属正确的模型证明设备代码正确。

华为[SIMT原子OR](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/910/API/ascendcopapi/docs/en/api/SIMT-API/atomic_operations/asc_atomic_or.md)说明950支持uint32 UB原子或；这里使用SIMT接口，不是只支持GM的SIMD标量同名接口。[整数popcount](https://asc.gitcode.com/api/SIMT-API/math_functions/integer_math_functions/__popc.html)使用`simt_api/device_functions.h`。驱动读取并记录黄区实际接口/实现头文件的声明及SHA256，实际9.2.0编译器仍须确认具体地址空间重载。

这次并非免费消除扫描：正常评分新增首次正分判断、散布原子置位以及位图清零。稠密查询下，原子冲突和寄存器变化可能抵消收益，甚至变慢。不能由旧PipeUtilization中向量占比高，推出本候选必然改善；也不需要先重采旧利用率。

## 独立验证合同

已验收基线仍是`large_scale_close1`。千万篇A/B原NPU约3.030/3.002ms，相对每轮更快的冻结CPU约1.93/1.95倍；该结果与源码保持原样。候选使用独立vendor：`bm25_fused_score_topk_scorebitmap_large`，不覆盖`bm25_fused_score_topk_large`或树合并vendor。

默认只在已测的10000000篇、固定Q8、每查询3词、K10验证。不再跑全部四档，也不增加查询批量冒充扩库。流程为：

1. 核对已完成大规模报告、六轮摘要、索引、参考、主机、两个CPU、安装对象和源码指纹；查询原始A/B编号保持不变。
2. 检查当前主机、HBM及磁盘预算，读取实际SIMT atomic/popcount头文件；只构建、安装一个候选融合算子并检查实际ABI/950对象。
3. 复用54次原始选择检查器，验证`debug=2`保留的稠密扫描路径。真实评分路径则用新8193篇定向语料：同owner字32位并发置位、1023/1024/1025正分边界、重复词、全零、同分、全局编号和尾叶。新旧NPU都对原文档独立参考及所有树层验收，完整输出位模式还须相同。合并未改，不再重复36次独立合并测试。
4. 在同一已存千万篇索引上运行六轮四角色：冻结原CPU、已验收NPU、候选NPU、冻结目录CPU，奇偶轮反转顺序，使两个NPU各先运行三次。每角色每轮5次A/B预热、30次A/B正式样本；完整Search计时合同原样保留。
5. 新旧NPU每轮各四个完整检查点的所有分数、每层Top-K分数位模式和编号逐文件相同；同时保留原索引回读、保护区、独立严格排名与交替查询前后检查。

预先固定的保留门禁，A/B两组都必须满足：

- 对同期已验收NPU，六轮批次中位数全部更低；六轮中位数汇总至少降低5%；p95的六轮中位数更低。
- 对同期两份冻结CPU，每轮取更快者，候选六轮全部更快，并通过原p95门禁。

5%是这次新候选的预定工程保留阈值，用于避免因微小抖动更换已达标版本；它没有修改既有MT大规模目标。即使候选正确且仍快于CPU，若不能稳定改善当前NPU，也不保留为新基线。未通过保留门禁返回2；编译、接口、预算或正确性失败返回1；所有门禁通过才返回0。失败目录和原vendor都保留。

新实验保留24个进程、各四份全分数检查点，千万篇约30.72 GB输出，加1 GiB余量，运行前至少需约31.8 GB可用磁盘。原索引与既有结果另计。驱动会先检查资源，不删除旧证据。若资源不足，报告未测，不产生性能结论。

## 本地状态与黄区命令

232组评分/位图/压缩模型、旧owner错误回归、同字冲突、源码隔离、8193篇独立参考及六轮保留门禁本地检查已通过。原已验收CPU、叶块、合并、主机、数据工具及验证器源码字节保持不变。**候选尚未CANN编译或设备执行，没有候选性能结论。**

提交时要重新`git add`更新后的三个Python文件；索引里此前暂存的是旧草稿。建议备注：`feat: 修正评分位图并增加千万篇新旧NPU配对验证`。

提交推送后，在黄区执行：

```bash
cd /test/w50066029/bm25-npu &&
git pull --ff-only &&
source /usr/local/Ascend/cann-9.2.0/set_env.sh &&
python3 -B verify_package.py &&
set -o pipefail &&
python3 -u -B standalone/score_bitmap.py \
  --output results/score_bitmap_large_close1 \
  2>&1 | tee results/score_bitmap_large_close1.log
```

默认读取`results/large_scale_close1/report.json`，沿用其中的设备5。输出目录和候选vendor必须是新的；无需重跑`large_search.py`。编译失败会在同一终端打印实际日志尾部；成功完成后打印`Paired large-scale bitmap decision`，主报告为`results/score_bitmap_large_close1/report.json`。请回传这次命令从开始到结束的终端文本；任何“更快”结论都要等这份A5结果。
